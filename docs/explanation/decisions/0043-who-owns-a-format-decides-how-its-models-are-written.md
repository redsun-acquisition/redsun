# 43. Who owns a format decides how its models are written

Date: 2026-11-26

## Status

Accepted

## Context

`redsun` describes two kinds of JSON document with `pydantic` models, and
the two can be made in opposite directions. Either you write the models in
Python and export the JSON Schema from them, or you start from a JSON Schema
and let `datamodel-code-generator`, a tool that turns a schema into
`pydantic` classes, write the models for you. Both are in the project now,
so a contributor adding a third kind of document needs to know which way to
go.

The [web session](../glossary.md#web-session) serves a document describing
its events in the AsyncAPI 3.0.0 format. The AsyncAPI project publishes the
JSON Schema of that format, so the models only have to follow it, and
`scripts/generate_asyncapi_models.py` generates them:

```python
# generated by datamodel-codegen:
#   filename:  asyncapi-3.0.0-subset.json
class Info(BaseModel):
    model_config = ConfigDict(extra="forbid", populate_by_name=True)
    title: Annotated[str, Field(description="A unique and precise title of the API.")]
```

The [reports](../glossary.md#report) of the `redsun` command have no such
source, because `redsun` defines their format itself. Their models carry a
docstring under each field, which becomes the field's description in the
schema, and they hold behaviour of their own:

```python
class Report(BaseModel, frozen=True, use_attribute_docstrings=True):
    redsun: str
    """The version of `redsun` that wrote the report."""

    def to_json(self) -> str: ...
```

A generated module would lose both, since generation rewrites the whole file
and nobody may edit it by hand.

## Decision

**A format someone else owns gets generated models, and a format `redsun`
owns gets models written by hand.** When the JSON Schema comes from a
standard, the committed copy of that schema is the source and the module is
generated from it. When `redsun` defines the format, the Python model is the
source and the schema is exported from it.

Either way, a test fails when the committed file differs from a fresh
generation or export. The generated module is checked with
`generate_asyncapi_models.py --check`, and the report schemas under
`schemas/` are compared with what the models export.

## Consequences

- A new document that follows a published standard starts from a cut-down
  copy of the standard's schema in `scripts/`, with its licence, and a script
  that generates the module and has a `--check` mode.
- A new report, or any other format `redsun` defines, is a model in Python
  with a docstring under each field. Its schema is exported, committed and
  checked by a test.
- `datamodel-code-generator` stays a development dependency. A session never
  imports it, because the generated module is committed.
