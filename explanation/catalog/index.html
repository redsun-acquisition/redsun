How the session catalog works¶

A session whose storage section has a catalog key runs a tiled server on this machine, from build to shutdown, to hold its catalog. Keep a catalog of runs shows how to use it.

What redsun does¶

redsun starts the server, keeps its database in <base_dir>/<session>/catalog, and gives its address to any component that asks for a CatalogAddress. It registers nothing in the catalog itself. Acquisition bytes belong to the service and its device (ADR 0013), and the session's components decide whether runs are recorded. Step through to see who does what:

The server reads application/x-ome-zarr files with ome-tiled, whose consolidator the session registers for TiledWriter. A consolidator turns a StreamResource and its StreamDatum documents into one catalog entry; this one reads the image's shape, chunks and axis names from its store rather than from the documents.

One catalog per session¶

A catalog indexes only the runs of its own session, so to ask a question across sessions you open each catalog. In exchange, everything a session produced lives under one directory, which you can archive or delete as a unit.

Writing to registered files¶

Registering a file doesn't protect it: tiled's write, write_block and patch reach a registered file like any other, and management=external forbids nothing. write_block is the hardest to notice, since it replaces one chunk and the file still reads correctly.

A client can overwrite a registered file

redsun calls none of these routes, but a component holding a client can. If your component writes into the catalog, have it create its own nodes, as client[run_uid].write_array(...) does, and leave registered ones alone.
